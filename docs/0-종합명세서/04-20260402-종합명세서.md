## 2. 개발 환경 동기화 설정 (팀 세팅 가이드)

프로젝트를 새로 클론(Clone)하거나 다른 PC에서 환경을 세팅할 때 **반드시 아래 절차를 동일하게 수행**해야 합니다.

### 2.1 터미널 환경 세팅 (Git Bash 필수)
Windows 기본 제공 PowerShell 5.1은 `&&` 명령어 체이닝과 한글 인코딩을 제대로 지원하지 못합니다.
1. [Git for Windows](https://git-scm.com/download/win)가 설치되어 있는지 (`C:\Program Files\Git\bin\bash.exe`) 확인합니다.
2. **VS Code**에서 `Ctrl + Shift + P` → `Terminal: Select Default Profile` 검색.
3. 목록에서 **`Git Bash`** 선택.
4. VS Code 터미널 탭을 전부 닫고 새 터미널(`Ctrl + ~`)을 열어 프롬프트가 `$` 형태(Bash)인지 확인합니다.

### 2.2 패키지 설치
모노레포 형태로 구성되어 있으나, 루트 디렉토리에서 패키지를 한 번에 관리하지 않고 client와 server를 각각 관리합니다.
```bash
# Git Bash 터미널 환경
npm install # (루트에 package.json이 있는 경우: concurrently 용도)
cd client && npm install
cd ../server && npm install
```

### 2.3 환경변수 (.env) 설정
`server/.env` 파일을 생성하고 아래 값들을 주입합니다. (보안상 실제 값은 팀 내 1Password 등 공유 수단 참조)
```env
DATABASE_URL=postgresql://postgres:{PASSWORD}@caboose.proxy.rlwy.net:5432/railway
JWT_SECRET=당신의_시크릿_키
PORT=5050
NODE_ENV=development
GOOGLE_APPLICATION_CREDENTIALS=./google-credentials.json
GOOGLE_DRIVE_CLIENTS_ROOT_FOLDER_ID=드라이브_루트_ID
GOOGLE_SHARED_DRIVE_ID=공유_드라이브_ID
GOOGLE_PLACES_API_KEY=구글_장소_API_키
GEMINI_API_KEY=제미나이_API_키
NAVER_CLIENT_ID=네이버_클라이언트_ID
NAVER_CLIENT_SECRET=네이버_클라이언트_시크릿
TELEGRAM_BOT_TOKEN=        # 개발 환경에서는 웹훅 충돌 방지를 위해 비워둡니다.
OUTSCRAPER_API_KEY=아웃스크래퍼_API_키
```
추가로 `server/google-credentials.json` 파일(GCP 서비스 계정 키)을 배치해야 합니다.

### 2.4 데이터베이스 마이그레이션 확인
동일한 원격 Railway DB를 바라보고 있다면 별도의 `db:push`는 필요 없으나, 스키마 변경 시 아래 명령어를 사용합니다.
```bash
cd server
npx drizzle-kit push --config=./drizzle.config.ts
```

### 2.5 로컬 서버 실행
```bash
# 루트 디렉토리에서 실행 (concurrently로 Client와 Server 동시 실행)
npm run dev
# 접속 주소: http://localhost:5173 (Vite 프론트엔드)
```

## 3. 프론트엔드 아키텍처 및 상태 관리 (TanStack Query)

2026-04-02 업데이트로 로컬 상태(`useEffect` + `setXxx`)의 비효율성을 제거하고, **TanStack Query 전역 캐싱 아키텍처**로 완전히 마이그레이션되었습니다.

### 3.1 캐싱 인프라 (`client/src/lib/`)
- `queryClient.ts`: 전역 `QueryClient` 설정. 데이터 만료 시간(staleTime) 등 공통 규칙 정의.
- `api.ts`: axios 또는 fetch 기반의 공통 데이터 통신 모듈.

### 3.2 핵심 커스텀 훅 (`client/src/hooks/`)
비즈니스 로직과 API 페칭을 UI 컴포넌트에서 분리하기 위해 기능별 커스텀 훅을 사용합니다.
| 훅 이름 | 관리 데이터 | Query Key | 기본 StaleTime |
|---------|------------|-----------|---------------|
| `useClients.ts` | 거래처 목록 | `['clients']` | 5분 |
| `useTemplates.ts` | 업무 템플릿 | `['templates']` | 5분 |
| `useUsers.ts` | 사용자/직원 목록 | `['users']` / `['admin-users']` | 2분~5분 |
| `useDriveFiles.ts` | 폴더/검색별 드라이브 파일| `['drive-files', folderId, query]` | 1분 |
| `useTasks.ts` | 업무 칸반 트리 | `['tasks']` | 1분 |
| `useMonitoring.ts`| 모니터링 템플릿 및 결과| `['monitoring-templates']` | 30초 |
| `useQuotations.ts`| 견적서 목록 | `['quotations']` | 1분 |
| `useContracts.ts` | 계약서 목록 | `['contracts']` | 1분 |
| `useServices.ts` | 서비스 상품 마스터 | `['services']` | 5분 |

### 3.3 로컬-서버 상태 동기화 패턴
마이그레이션 과도기를 거치며, 기존의 `state` 기반 UI 편집 로직(예: 드래그앤드롭)을 깨지 않기 위해 아래 패턴을 차용합니다:
```typescript
const { data: serverData } = useQuery({ queryKey: ['tasks'], queryFn: fetchTasks });
const [localData, setLocalData] = useState([]);

useEffect(() => {
    if (serverData) setLocalData(serverData);
}, [serverData]);
```
추후 CRUD 시에는 `queryClient.invalidateQueries({ queryKey: ['tasks'] })`를 호출하여 서버와 UI를 동기화합니다.

## 4. 백엔드 및 데이터베이스 스키마

Railway PostgreSQL 상에 총 20개 이상의 테이블이 Drizzle ORM으로 관리되고 있습니다.

### 4.1 핵심 모듈 구조
```
server/src/
 ├── db/schema.ts         # 🔥 데이터베이스 단일 진실 공급원 (Single Source of Truth)
 ├── middleware/auth.ts   # JWT 토큰 해독 및 Role 기반(ADMIN, MANAGER 등) 라우터 보호
 ├── routes/              # Express 컨트롤러 및 라우팅 명세 (도메인별 분리)
 └── services/            # 타사 API, 스크래핑, 복잡한 비즈니스 트랜잭션 등 추상화 계층
```

### 4.2 주요 ERD 관계 요약 (CASCADE 정책 주의)
- **`clients` (거래처)** 가 시스템 데이터의 중심축. 많은 테이블(`users`, `tasks`, `monitoring_templates`, `quotations`, `contracts`)이 `clientId`를 외래키로 참조합니다.
- 거래처 삭제 시, `contracts`, `service_contracts` 등은 `CASCADE`로 날아가지만 유저나 업무 데이터 등은 `SET NULL`을 통해 보존하는 방식을 띱니다. 
- 서비스 상품 마스터(`services` → `service_tiers`, `service_items` → `item_prices`)는 완전한 CASCADE 관계를 갖습니다.

### 4.3 모니터링/스크래핑 엔진 (`server/src/services/monitoring/`)
- 네이버 API, 구글 플레이스(Outscraper API), 카카오맵(Playwright Vision 스크래핑) 등을 하이브리드로 수집합니다.
- 게시글 본문을 뽑아와 `Gemini-2.5-Flash` 모델을 통해 감성 분석 및 리뷰 핵심 요약을 진행합니다.
- **스케줄러(`schedulerService.ts`)**: 30초 틱의 Node.js 내부 인터벌로 트리거를 돌며, 설정된 cron 수식에 맞춰 자동 모니터링을 백그라운드에서 비동기 실행합니다.

## 5. 컴포넌트 규칙 및 설계 지침 (개발 제약 사항)

### 5.1 파일 크기 제한 가이드
- **Soft Limit (1000줄)**: React 페이지 컴포넌트 하나의 크기가 1000줄을 넘어가는 경우(예: 현재 `AdminPage.tsx`, `MonitoringPage.tsx`), 즉각적으로 서브 컴포넌트로 모듈화하거나 상태 로직을 Hook으로 추출해야 합니다.

### 5.2 모달/팝업 통일
- 신규 등록/수정 동작은 가급적 **모달(Modal) 혹은 바텀 시트(Sheet)** 형태의 UI를 가지며, 페이지 이동으로 인한 Context 상실을 방지합니다. 
- `ExpandedColumnModal` 등 공용 모달을 응용하여 개발합니다.

### 5.3 브라우저 인가(Auth) 에러 처리 (권한 403 분리)
- 서버에서 403 에러가 발생한 경우, TanStack Query의 `error` 핸들러가 이를 캐치하고 전역 Toast로 접근 거부 알림을 표시해야 합니다. (직원 권한 레벨을 반드시 준수할 것)

## 6. 배포 파이프라인 (Railway)

### 6.1 Docker 빌드
프로젝트 루트의 `Dockerfile`은 멀티 스테이지를 사용하지 않고 바로 빌드/서빙하는 형태의 설정을 가지고 있습니다. (Playwright 크롬 드라이버 종속성 문제를 함께 해결하기 위해 `node:20-slim` 위에 시스템 라이브러리를 직접 탑재)

### 6.2 배포 흐름
1. `github`의 `develop` 및 `main` 브랜치에 코드가 병합(Push)되면 Railway에서 웹훅을 수신.
2. Railway 빌드 봇이 Dockerfile을 읽어 `npm run build` 진행.
3. 빌드 후 `node dist/server/src/index.js` 가 Entry 명령어로써 실행되며 (포트는 동적 할당).
4. SPA(싱글 페이지 앱) 라우팅을 리다이렉트하기 위해, 서버가 `/api/*` 이외의 경로는 `index.html`을 정적 서빙하도록 설정되어 있습니다.
